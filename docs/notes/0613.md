# OpenSpec 定制化：打造契合团队的工作流引擎

> OpenSpec 是一个开源、Schema 驱动的工作流框架，它定义了从「提案」到「归档」的完整变更生命周期。但开源工具拿过来不是终点，定制化才是让它贴合团队基因的关键。

---

## 为什么需要定制化？

**核心矛盾：开源框架的通用性 vs 团队实践的独特性。**

OpenSpec 的设计哲学是"约定优于配置"，它提供了 artifact（产物）的概念——每个 artifact 代表变更过程中的一个里程碑文档，如 `proposal.md`、`specs.md`、`design.md`、`tasks.md`。但默认约定不一定适合所有场景：

| 场景 | 默认 Openspec 的不足 | 定制方向 |
|------|---------------------|---------|
| 需要严格 TDD 流程 | tasks 不区分 RED/GREEN/REFACTOR 阶段 | 强制原子化 TDD 拆分 |
| 涉及前端开发 | 缺少 UI 设计规范和视觉验收 | 新增 design-system、ui-preview artifact |
| 修改老项目代码 | 缺少影响范围分析 | 新增 impact-analysis artifact |
| 公司要求交付 API 文档 | 缺少 API 契约产出 | 新增 api-contracts artifact |
| 公司要求手工测试用例 | 缺少测试用例产出 | 新增 manual-test-cases artifact |
| 质量门禁不自动化 | 缺少浏览器/接口自动化验证 | 新增 browser-test、verify-ui 技能 |

**总结一句话**：定制 OpenSpec = 定义"什么样的产出才叫完成" + "什么样的流程才能放心合并"。

CodingHub 项目针对这些痛点，在 OpenSpec 之上构建了两套定制化 Schema 和一套扩展技能体系，覆盖了从提案到自动化验证的完整闭环。

---

## 一、Schema 体系总览

OpenSpec 通过 YAML Schema 文件定义工作流。每个 Schema 描述了一组 artifact 及其依赖关系、生成指令。**项目中的所有变更都必须指定一个 Schema**，全局默认 Schema 在 `openspec/config.yaml` 中配置。

目前 CodingHub 维护了 4 个 Schema，按复杂度递增：

```
tdd-with-apply                  ← 极简版：proposal → specs → design → tasks
  └── tdd-with-execute-plan     ← 基础版：省去 plans，直接执行 tasks
       └── tdd-with-execute-plan-speckit-like   ← 完整版：+ API 契约 + UI 预览 + 手工测试
       └── ui-design-to-browser-test            ← 全栈版：+ 设计系统 + 影响分析 + 浏览器测试
```

**项目级配置**（`openspec/config.yaml`）：

```yaml
schema: ui-design-to-browser-test
project: CodingHub
backend:
  language: Java 17
  framework: Spring Boot 3.2.5
  build: Gradle
frontend:
  language: TypeScript
  framework: Vue 3.4.21
  build: Vite
database:
  type: MySQL 8.x
  db: ai_tool_square
superpowers:
  plans_dir: docs/superpowers/plans/
```

## 二、Artifact 定制化

Artifact 是 OpenSpec 的核心概念——每次变更就是按 Schema 定义的顺序逐个生成 artifact。定制 artifact 分两类：

### 2.1 修改原有 artifact 的产出要求

不新增 artifact，但收紧其内容标准。例如：

#### (a) 规定 specs 使用 GIVEN/WHEN/THEN 格式

默认 OpenSpec 对 specs 格式没有硬性约束。通过修改 Schema 中的 instruction 字段，强制行为规格必须用标准 BDD 格式书写。

**Schema 配置**（`schema.yaml` 中的 specs artifact）：

```yaml
- id: specs
  generates: specs/**/*.md
  description: 行为规格——用场景描述期望行为
  template: spec.md
  instruction: |
    用 GIVEN/WHEN/THEN 格式编写行为规格：
    - 每个场景必须可独立测试
    - 覆盖：正常路径、边界情况、错误处理
    - 只描述期望行为，不描述实现方式
  requires:
    - proposal
```

**对应的模板文件**（`templates/spec.md`）：

```markdown
# Spec

## Scenarios

### Scenario 1: [name]
- GIVEN: [前置条件]
- WHEN: [操作]
- THEN: [期望结果]
```

**为什么这样定制？**
- GIVEN/WHEN/THEN 格式迫使思考前置条件，减少"想当然"的 bug
- 每个场景独立可测，天然适合后续拆分为 TDD 任务
- 行为描述与实现解耦，测试代码和 specs 能一一对应

#### (b) 规定 tasks 必须包含 TDD 阶段

默认 tasks 只是一串 checkbox 任务，不区分测试/实现/重构。通过定制 instruction，强制每个功能拆分 RED → GREEN → REFACTOR 三个阶段。

**Schema 配置**：

```yaml
- id: tasks
  generates: tasks.md
  description: 原子化TDD任务列表
  template: tasks.md
  instruction: |
    关键要求：将工作拆分为原子化 TDD 任务。
    每个任务必须是且仅是一个 TDD 阶段（RED / GREEN / REFACTOR）。
    必须使用checkbox格式书写每个任务：
    ### Feature: [功能名称]
    - [ ] RED: 编写失败测试——[测试什么行为]
    - [ ] GREEN: 最小实现——[实现描述，引用对应的RED任务]
    - [ ] REFACTOR: 重构清理——[清理描述]（可选）
    规则：
    1. 禁止将RED和GREEN合并到一个任务
    2. 每个GREEN任务必须引用对应的RED测试
    3. 每个任务必须使用"- [ ]" checkbox格式
    4. 任务严格交替：RED→GREEN→（可选REFACTOR）
    5. 每个任务应在2-5分钟内可完成
  requires:
    - specs
    - design
```

**生成的 tasks.md 效果示例**：

```markdown
# Tasks

## Atomic TDD Task List

### Feature: 工具搜索
- [ ] RED: 编写失败测试——当搜索关键词为空时返回所有工具
- [ ] GREEN: 最小实现——ToolService.search() 方法，实现空关键词逻辑
- [ ] REFACTOR: 重构清理——抽取 search query builder 到独立方法

### Feature: 工具分页
- [ ] RED: 编写失败测试——验证分页参数 page=1, size=10 返回正确数据切片
- [ ] GREEN: 最小实现——ToolController 分页查询，使用 Pageable
```

**为什么这样定制？**
- 强制执行 TDD 纪律：不写测试就别想写实现代码
- 原子化保证进度可视：每个任务 2-5 分钟，`openspec status` 立刻看到谁在做什么
- GREEN 必须引用 RED，形成可追溯的责任链

### 2.2 新增 artifact——按需扩展工作流产出

当团队有额外交付物要求时，在 Schema 中新增 artifact 是最自然的方式。以下是 CodingHub 实践中新增的 artifact。

#### (a) UI 设计系统文档 (`design-system.md`)

**场景**：涉及前端页面的变更，需要一份明确的 UI 约束文档，统一团队对样式、组件、交互的认知。

**Schema 配置**：

```yaml
- id: design-system
  generates: design-system.md
  description: |
    本次变更的 UI 约束摘要——引用全局设计系统，列出本次涉及的组件/样式/交互规范
    【可选 artifact】仅当改动涉及前端 UI 时生成；纯后端/逻辑变更可跳过
    【双主题固定配置】项目始终使用暗色 (dark) + 亮色 (light) 双主题
  template: design-system.md
  instruction: |
    ## 第一步：读取全局设计系统
    读取项目全局设计系统文件 `design-system/CodingHub/MASTER.md`

    ## 第二步：按需补充 ui-ux-pro-max 检索
    如全局设计系统未覆盖，调用 ui-ux-pro-max 补充

    ## 第三步：生成本次 UI 约束摘要
    必须包含的章节：
    1. 全局样式引用 — 字体、圆角、阴影
    2. 双主题 Tokens 映射 — 暗色主题 | 亮色主题 | CSS 变量 三列表
    3. 涉及组件清单
    4. 交互状态（双主题）— 每个组件按暗色/亮色分别列出
    5. 响应式策略
    6. 可访问性要求 — checkbox 清单
    7. 图标清单 — Lucide 图标及 aria 属性
    8. Antipatterns 检查
  requires:
    - proposal
```

**生成的双主题 Token 映射表示例**：

```markdown
## 2. 双主题 Tokens 映射

| 角色 | 暗色主题 | 亮色主题 | CSS 变量 |
|------|----------|----------|----------|
| 页面背景 | `#09090b` | `#f8fafc` | `--bg-primary` |
| 面板/侧栏 | `#0f0f12` | `#f1f5f9` | `--bg-secondary` |
| 卡片背景 | `rgba(15,15,20,0.7)` | `rgba(255,255,255,0.9)` | `--bg-card` |
| 主色 (紫) | `#8b5cf6` | `#7c3aed` | `--accent-1` |
| 辅助色 (青) | `#06b6d4` | `#0891b2` | `--accent-2` |
| 主文字 | `#fafafa` | `#0f172a` | `--text-primary` |
| 次文字 | `#a1a1aa` | `#475569` | `--text-secondary` |
| 焦点评点环 | `#00FFFF` | `#7c3aed` | `--focus-ring` |
```

**每个组件的交互状态分别列出暗色/亮色两套样式**：

```markdown
## 4. 交互状态（双主题）

### 4.1 StatsCard — 暗色主题

| 状态 | 样式 |
|------|------|
| normal | `background: var(--bg-card); border: 1px solid var(--border-color);` |
| hover | `border-color: var(--border-glow); box-shadow: 0 0 20px rgba(139,92,246,0.15);` |
| focus | `outline: 2px solid #00FFFF; outline-offset: 2px;` |

### 4.2 StatsCard — 亮色主题

| 状态 | 样式 |
|------|------|
| normal | `background: var(--bg-card); border: 1px solid var(--border-color);` |
| hover | `border-color: var(--border-glow); box-shadow: 0 0 20px rgba(124,58,237,0.1);` |
| focus | `outline: 2px solid #7c3aed; outline-offset: 2px;` |
```

**定制价值**：
- 设计师和开发共用同一份约束文档，减少"做出来不对"的返工
- 双主题并行定义，杜绝"只做了暗色忘了亮色"的遗漏
- 可访问性和 Antipatterns 检查清单嵌入 artifact，形成验收标准

#### (b) UI 预览 HTML (`ui-preview.html`)

**场景**：在编码实现之前，先出一份可在浏览器中预览的 HTML 原型，作为视觉验收标准。

**Schema 配置**：

```yaml
- id: ui-preview
  generates: ui-preview.html
  description: |
    HTML 界面预览——基于设计系统与 ui-ux-pro-max 设计规范生成可交互的 UI 原型
    【仅当改动涉及前端 UI 时生成】
  template: ui-preview.md
  instruction: |
    使用 ui-ux-pro-max skill 获取设计规范与样式决策，然后生成 HTML 预览页面。

    双主题 CSS 变量方案：
    - 在 :root 中定义暗色主题的全部 CSS 变量
    - 使用 [data-theme="light"] 选择器覆盖亮色主题
    - 页面 <html> 初始设置 data-theme="dark"
    - 提供主题切换按钮，通过 JS 切换 data-theme 属性

    生成要求：
    1. 必须生成可独立运行的 HTML 文件（内联 CSS + JS，无外部依赖）
    2. 包含页面主要状态的预览：正常态、悬停态、聚焦态、加载态、空状态、错误态
    3. 覆盖桌面/平板/移动端响应式布局
    4. 所有图标使用内联 SVG（Lucide），禁止 emoji
    5. 包含基础可访问性标记（语义标签、aria-label、focus-visible）
    6. 文件保存到 ui-preview.html
    7. 生成后使用 preview_url 工具打开预览
  requires:
    - design
```

#### (c) 代码影响范围分析 (`impact-analysis.md`)

**场景**：修改老旧项目代码时，需要知道"改这个类会波及哪些地方"。

**Schema 配置（条件必选——仅当修改现有代码时执行）**：

```yaml
- id: impact-analysis
  generates: impact-analysis.md
  description: |
    代码影响范围分析——基于 design.md 中的文件/类清单执行 codegraph 扫描
    【条件必选】仅当 design 涉及修改现有代码时执行；纯新增模块/页面可跳过
  template: impact-analysis.md
  instruction: |
    1. 读取 design.md 中的文件列表、类列表
    2. 判定改动类型：
       - 全部新增 → 跳过
       - 存在现有文件 → 必须执行
    3. 使用 Task(code-explorer) 子代理扫描代码库：
       - 追踪直接调用方与传递调用方（深度 2-3 层）
       - 列出依赖的上游服务（repository、config、util）
       - 找出受影响的测试文件
       - 评估改动风险等级（L0/L1/L2）
       - 生成回归测试建议清单
    4. 校验后端层级依赖仍合法：
       bash scripts/lint-arch.sh
    5. 若发现 design.md 漏掉受影响文件/测试，列出"设计修正建议"
  requires:
    - design
```

**生成的影响分析报告示例**：

```markdown
# Impact Analysis

## 1. 改动范围

| 类型 | 数量 | 文件列表 |
|------|------|----------|
| 新增 | 3 | ToolSearchService.java, ToolSearchServiceTest.java, SearchController.java |
| 修改 | 2 | ToolService.java, ToolController.java |
| 删除 | 0 | - |

## 2. 调用图

### 反向调用图（被谁调用）

```
ToolService.search()
  ├── ToolController.search() (ToolController.java:45)
  │     └── GET /api/tools?keyword=xxx (API endpoint)
  └── HomeController.index() (HomeController.java:30)
```

### 直接调用方

| 调用方 | 位置 | 风险等级 |
|--------|------|----------|
| ToolController.search() | ToolController.java:45 | L1 |
| HomeController.index() | HomeController.java:30 | L1 |

## 3. 受影响的测试

| 测试文件 | 类型 | 状态 | 行动 |
|----------|------|------|------|
| ToolServiceTest.java | 单元 | 需更新 | 新增 search() 测试用例 |
| ToolControllerTest.java | 集成 | 需更新 | 新增 /api/tools?keyword 测试 |

## 5. 风险评估

**本次改动风险等级**: L1（修改公共 API service 方法签名）

## 6. 层级依赖校验

bash scripts/lint-arch.sh
结果: PASS

## 7. 回归测试建议

- [ ] ToolService.search() —— 验证关键词搜索返回正确结果
- [ ] ToolController.search() —— 验证 API 端点搜索功能
- [ ] HomeController.index() —— 验证首页搜索集成
```

**定制价值**：
- 条件必选：新功能不改老代码则自动跳过，避免无效工作
- 自动 codegraph 扫描保证不漏掉隐藏的调用链依赖
- lint-arch.sh 自动化检查架构分层是否被破坏

#### (d) API 接口契约 (`api-contracts.md`)

**场景**：公司交付流程要求输出标准的 API 接口文档。

**Schema 配置**：

```yaml
- id: api-contracts
  generates: api-contracts.md
  description: API接口契约——对外API接口描述、入参返回值字段定义与示例
  template: api-contracts.md
  instruction: |
    每个接口必须包含：
    - HTTP方法和路径、接口描述、认证要求
    - 请求参数（路径/查询/请求体），包含字段名、类型、是否必填、默认值、描述
    - 请求体示例（JSON格式）、输入校验规则
    - 成功响应（状态码、响应体字段定义、示例JSON）
    - 错误响应、通用响应结构说明、通用错误码定义
  requires:
    - specs
    - design
```

**生成的 API 契约文档示例**：

```markdown
# API Contracts

## Common Response Structure

所有API响应遵循统一信封格式：

```json
{
  "code": 200,
  "message": "success",
  "data": { ... }
}
```

错误码定义：

| code | meaning |
|------|---------|
| 200 | 成功 |
| 400 | 请求参数无效 |
| 401 | 未认证 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 500 | 服务器内部错误 |

---

## Tool APIs

### GET /api/tools — 获取工具列表

**描述**: 分页查询工具列表，支持关键词搜索和分类筛选

**认证**: 公开

**查询参数**:

| param | type | required | default | description |
|-------|------|----------|---------|-------------|
| keyword | string | No | - | 搜索关键词 |
| categoryId | long | No | - | 分类ID筛选 |
| page | int | No | 0 | 页码（从0开始） |
| size | int | No | 10 | 每页数量 |

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "content": [
      {
        "id": 1,
        "name": "ChatGPT",
        "categoryId": 1,
        "categoryName": "对话助手",
        "description": "OpenAI 推出的 AI 对话工具",
        "uploaderName": "admin",
        "createdAt": "2026-06-10T10:00:00"
      }
    ],
    "totalElements": 100,
    "totalPages": 10,
    "page": 0,
    "size": 10
  }
}
```

**响应字段说明**:

| field | type | description |
|-------|------|-------------|
| content | array | 工具列表 |
| content[].id | long | 工具ID |
| content[].name | string | 工具名称 |
| totalElements | long | 总记录数 |
| totalPages | int | 总页数 |
```

## 三、Skill/Command 定制化

Artifact 是"产出什么"，Skill/Command 是"流程中多做什么"。CodingHub 新增了四个关键技能，覆盖从计划生成到质量验证的完整阶段。

### 3.1 生成 Superpowers 实现计划 (`/opsx:write-plan`)

**场景**：tasks.md 完成后，将 OpenSpec 的原子化 TDD 任务转化为 Superpowers 可以执行的实现计划文件。

**命令入口**（`.codebuddy/commands/opsx/write-plan.md`）：

```markdown
---
name: OPSX: Write Plan
description: "Use when an OpenSpec change has proposal, design, and tasks artifacts
ready and a Superpowers implementation plan needs to be created before execution."
---

Generate a detailed Superpowers implementation plan from an OpenSpec change's artifacts.

**Input**: Optionally specify a change name. Supports --max-tasks N (default 20).

**Steps**:

1. Select the change → openspec status --change '<name>' --json
2. Parse tasks.md to extract all task labels (e.g., 1.1, 2.3)
3. Determine plan splitting:
   - If total tasks > max-tasks → split into ceil(total / max-tasks) groups
   - Present splitting plan to user for confirmation
4. Call superpowers:writing-plans with OpenSpec artifacts as context
5. Each plan task must include <!-- openspec-task: LABEL --> annotation
6. Verify mapping coverage — every OpenSpec label must have ≥1 plan task
7. Output summary with plan file paths

**File naming**:
- Single plan: docs/superpowers/plans/YYYY-MM-DD-<change-name>.md
- Multiple plans: docs/superpowers/plans/YYYY-MM-DD-<change-name>-tasks-<n>-<m>.md
```

**关键设计**：

1. **任务标签映射**：每个 Superpowers plan task 通过注释 `<!-- openspec-task: 1.1 -->` 与 OpenSpec tasks.md 中的 label 绑定，保证执行完成后能精确回写状态。

   生成的 plan 文件示例：
   ```markdown
   # Implementation Plan: add-tool-search

   <!-- openspec-task: 1.1 -->
   ### Task 1: Write failing test for empty keyword search

   - [ ] Create test class ToolSearchServiceTest.java
   - [ ] Write test: when keyword is empty, return all tools
   - [ ] Run test → verify FAIL (RED)

   <!-- openspec-task: 1.2 -->
   ### Task 2: Implement empty keyword logic

   - [ ] Implement ToolService.search() method
   - [ ] Handle null/empty keyword → return all tools
   - [ ] Run test → verify PASS (GREEN)
   ```

2. **自动拆分**：当 tasks.md 超过 20 个任务时（`--max-tasks 20`），自动拆分为多个 plan 文件。通过控制每个 plan 的任务数量，避免单个会话上下文过长导致执行质量下降。

   ```
   Total tasks: 21, max-tasks: 20 → 2 plans
   Plan 1: Tasks 1.1–2.3 (10 tasks)
   Plan 2: Tasks 2.4–5.1 (11 tasks)
   Proceed? [Y/n]
   ```

3. **映射验证**：生成完成后自动检查，确保没有 OpenSpec task label 被遗漏，也没有 plan 中引用了不存在的 label（如笔误 1.11 vs 1.1）。

---

### 3.2 执行实现计划并同步进度 (`/opsx:executing-plans`)

**场景**：plan 文件已生成，需要驱动 Superpowers 子代理执行实现，并将完成进度自动同步回 OpenSpec 的 tasks.md。

**命令入口**（`.codebuddy/commands/opsx/executing-plans.md`）：

```markdown
---
name: OPSX: Executing Plans
description: "Execute Superpowers implementation plans, sync completed work
back to tasks.md."
---

Execute Superpowers implementation plans for an OpenSpec change, then sync
completed tasks back to tasks.md.

**Steps**:

1. Select the change → openspec status --change '<name>' --json
2. Detect plan files in docs/superpowers/plans/ matching change name
3. Decision tree:
   - Plan exists + Superpowers → Execute
   - Plan exists - Superpowers → Suggest /opsx:apply as alternative
   - No plan + Superpowers → Ask: create plan first?
   - No plan - Superpowers → Suggest /opsx:apply as alternative
4. Offer execution choice:
   1. Subagent-Driven (recommended) — fresh subagent per task, review between
   2. Inline Execution — batch execution with checkpoints
5. Execute via Superpowers:
   - Subagent-Driven → superpowers:subagent-driven-development
   - Inline → superpowers:executing-plans
6. Sync tasks.md:
   - Parse <!-- openspec-task: LABEL --> from all plan files
   - Only mark label as [x] when ALL plan tasks under it are complete
   - Report: synced / still in progress / overall progress
7. Show final status → suggest /opsx:verify then /opsx:archive
```

**关键设计**：

1. **双向同步机制**：OpenSpec tasks.md 定义"做什么"，Plan 文件定义"怎么做"。执行完成后，通过 `<!-- openspec-task: 1.1 -->` 注释自动反向同步 —— 只有当一个 label 下所有 plan task 的 checkbox 都 `[x]` 时，才在 tasks.md 中标记完成。

   ```
   ## Task Sync Results

   Synced to tasks.md:
   - [x] 1.1 Write failing test for keyword search
   - [x] 1.2 Implement keyword search logic

   Still in progress:
   - [ ] 2.1 Implement pagination (2/3 plan tasks complete)

   Overall: 2/3 OpenSpec tasks complete
   ```

2. **执行模式选择**：
   - **Subagent-Driven**（推荐）：每个 task 启动一个独立子代理，task 之间可以暂停审查。适合需要质量把控的复杂变更。
   - **Inline Execution**：批量顺序执行，checkpoint 检查点。适合简单、连贯的变更。

3. **优雅降级**：如果 Superpowers 未安装，自动降级提示用户使用 `/opsx:apply` 直接执行 tasks.md，不阻断流程。

4. **部分完成追踪**：即使执行中断，已完成的 plan task 状态也会被保留和报告，下次 `/opsx:executing-plans` 可继续。

### 3.3 浏览器自动化测试 (`/opsx:browser-test`)

**场景**：功能开发完成后，在真实浏览器中验证页面行为，作为归档前的最后一道质量门禁。

**命令入口**（`.codebuddy/commands/opsx/browser-test.md`）：

```markdown
---
name: OPSX: Browser Test
description: "Execute browser E2E tests using opencli-browser after implementation"
argument-hint: "[change-name]"
---

Execute browser-based E2E tests for an OpenSpec change after implementation.

**Prerequisites**:
- All TDD tasks completed (RED/GREEN/REFACTOR)
- UI implementation tasks completed (if any)
- Unit tests passing
- Dev server running

**Steps**:

1. Check opencli environment:
   opencli doctor

2. Load the browser test skill:
   /openspec-browser-test

3. Determine what to test:
   openspec status --change "<name>" --json

4. Execute tests:
   opencli browser test open "<url>"
   opencli browser test wait selector "<selector>" --timeout 15000
   opencli browser test state
   opencli browser test find --css "<selector>"
   opencli browser test screenshot [<path>]
   opencli browser test close

5. Record results:
   | Test Case | Status | Notes |
   |----------|--------|-------|
   | TC-001   | ✅ PASS / ❌ FAIL | |
```

**对应的 tasks.md 中浏览器测试任务示例**：

```markdown
## C. Browser Test【如有 UI 改动】

> 开发任务完成后，手动加载 /openspec-browser-test skill 执行浏览器测试。
> 测试依据: specs、design.md、ui-preview.html

### Test: 工具列表页面

- [ ] TC-001: 工具列表页面加载——打开首页，验证工具卡片渲染、分页组件、搜素栏
- [ ] TC-002: 搜索功能——输入关键词，验证列表正确筛选，验证空结果状态
- [ ] TC-003: 主题切换——点击主题按钮，验证暗色/亮色切换，验证焦点环颜色变化
```

**为什么加入浏览器测试？**
- TDD 测试覆盖了后端逻辑，但前端交互（点击、hover、主题切换）只有真实浏览器能验证
- opencli 的 `screenshot` 命令截图留存，作为视觉回归的基线
- 在 tasks.md 中预先定义 TC-xxx，保证测试覆盖与功能需求对齐

### 3.4 UI 规范验证与自动修复 (`/opsx:verify-ui`)

**场景**：前端代码写完不代表符合设计规范——CSS 变量用了吗？暗色/亮色都适配了吗？焦点环正确吗？这个技能专门解决这类问题。

**命令入口**（`.codebuddy/commands/opsx/verify-ui.md`）：

```markdown
---
name: OPSX: Verify-UI
description: "Independent UI verification using ui-ux-pro-max, auto-fixes issues"
argument-hint: "[component-path or --fix or --all]"
---

# /opsx:verify-ui

独立的 UI 验证命令，使用 ui-ux-pro-max 设计系统检查 UI 实现质量，发现问题时自动修复。

## Quick Start
/verify-ui --fix          # 验证并自动修复所有组件
/verify-ui --all         # 验证所有 UI 组件
/verify-ui --check       # 只验证不修复
/verify-ui <path>        # 验证指定组件

## Auto-Fix 规则

### CSS 变量检查
- 发现 inline 颜色值 → 自动替换为 CSS 变量
- 对比 design-spec 中的 radius-lg/sm/md 值 → 替换为 var(--radius-*) 格式

### 组件结构
- 缺少 TypeScript 类型 → 自动添加
- 缺少 scoped styles → 自动添加
- 缺少 Props 定义 → 自动规范化

## 验证流程
1. 读取 design-system.md 获取设计规范
2. 读取组件源码
3. 对比设计规范与实现
4. 发现问题自动修复并写回
5. 生成验证报告

## Integration
/verify-ui --fix    # 验证并自动修复
    ↓
/verify-ui --check  # 验证下一个组件
    ↓
/opsx:archive       # 归档变更
```

**使用示例**：

```bash
# 开发完成后，验证所有新增/修改的前端组件
/verify-ui --fix frontend/src/pages/OverviewPage.vue
/verify-ui --fix frontend/src/components/StatsCard.vue
/verify-ui --fix frontend/src/components/RankItem.vue
```

**Auto-Fix 示例**：假设某个 Vue 组件中硬编码了颜色：

```vue
<!-- 修复前 -->
<style scoped>
.card {
  background: #09090b;
  color: #fafafa;
  border: 1px solid #333;
}
</style>

<!-- 自动修复后 -->
<style scoped>
.card {
  background: var(--bg-primary);
  color: var(--text-primary);
  border: 1px solid var(--border-color);
}
</style>
```

**为什么加入 UI 验证？**
- 人工 Code Review 容易遗漏样式问题，尤其是双主题一致性
- Auto-Fix 机制把枯燥的 CSS 变量替换自动化，人只做决策
- 在归档前跑一遍，保证所有 UI 改动都符合设计系统，不需要后续返工

## 五、定制化总结

| 定制层级 | 定制方式 | 案例 |
|----------|---------|------|
| **Artifact 要求** | 修改 instruction（收紧标准） | specs 强制 GIVEN/WHEN/THEN；tasks 强制 TDD 三阶段 |
| **Artifact 新增** | 在 schema.yaml 中添加新 artifact | design-system、ui-preview、impact-analysis、api-contracts、manual-test-cases |
| **Skill/Command 新增** | 编写 SKILL.md + command.md | browser-test（浏览器 E2E）、verify-ui（UI 自动验证+修复） |
| **条件逻辑** | artifact 中判断是否需要执行 | design-system/ui-preview 仅在 UI 改动时生成；impact-analysis 仅在修改现有代码时执行 |
| **工具链嵌入** | instruction 中调用外部工具 | ui-ux-pro-max 检索设计规范；code-explorer 扫描代码库；lint-arch.sh 检查架构 |

**核心原则**：

1. **Schema 即契约**：Schema YAML 定义了"什么是完成"，团队所有人对交付标准达成一致
2. **条件必选减少噪音**：纯后端变更不生成 UI artifact，纯新增代码不跑影响分析
3. **证据驱动不可跳过**：TDD 的 RED 必须失败、GREEN 必须通过，浏览器测试必须有截图留存
4. **自动化前置**：verify-ui 的 auto-fix 机制让规范检查从"人提醒人"变成"工具提醒人"

OpenSpec 的定制化本质上是**把团队的最佳实践编码化**——不是每次从头写检查清单，而是把检查清单变成 Schema 的 instruction、变成 Skill 的验证步骤。这样每次变更都在同一个高标准下执行，质量不再依赖个人自觉。
