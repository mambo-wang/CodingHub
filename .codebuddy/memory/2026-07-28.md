## 结构分析：analyze_impact 对 Java 实体类的局限性

- 用 `analyze_impact(file_paths=['.../model/ToolLike.java'], direction='depended_by')` 删除影响评估时，工具**只返回类自身**（含 `@onCreate` 方法），漏报了真实依赖方。
- 根因：CodeWiki 调用图只追踪**方法调用边**，不追踪 Java 的**泛型/字段类型/import 引用**。JPA 实体（`ToolLike`）被 `ToolLikeRepository extends JpaRepository<ToolLike, Long>` 和测试 `@Mock ToolLikeRepository` 引用，但这些是类型引用而非调用，故不在图里。
- 正确做法：评估「删除某类」的影响时，**必须用 `search_content` 全仓库搜类名 + Repository 名核实**，不能只信 `analyze_impact` 结果。`UnifiedLikeService` 里的 `buildToolLikes` 方法名含子串 "ToolLike" 但并未引用该类型，属搜索假阳性，需人工辨别。
- 本案中 ToolLike 体系已是 `@Deprecated` 死代码，真实业务已迁到 `UnifiedLike` 体系。

## 影响评估：Video.commentCount 类型修改

- 用 analyze_impact + 全文检索交叉验证评估了 `Video.commentCount` 改类型的爆炸半径：低-中风险（~12 类，集中在微课+统一互动模块，depth≤2）。
- 受影响：`Video`（updateScore/incrementCommentCount/Lombok）、`UnifiedCommentService`(L288/L315 `Math.max` 拆箱)、`VideoService`(L396/L432)、`UnifiedLikeService`/`UnifiedFavoriteService`（映射+内部DTO）、`VideoResponse`/`VideoListItem` DTO、5 个测试类的 builder 字面量。
- 最大风险：DB `video.comment_count` 列迁移 —— Hibernate `ddl-auto: update` 不会变更已有列类型，INT→BIGINT 须手写 Flyway 迁移（MySQL `MODIFY` / PG `ALTER COLUMN TYPE`），双库都要覆盖。
- 再次验证：analyze_impact 漏报 Lombok getter/setter 引用（非方法调用边），实体字段级改动必须补 `search_content` 全仓搜索。
