## RAG 下载超时根因修复（HF_ENDPOINT 未走镜像）

报错 `Connection to huggingface.co timed out` 的真正根因有两点：
1. `huggingface_hub` 在 import 时把 `HF_ENDPOINT` 缓存为模块级常量（`constants.HF_ENDPOINT = os.getenv(...)`），之后改 `os.environ` 无效。原代码镜像设置写在 `from sentence_transformers import SentenceTransformer` **之后**，此时常量早已固定成官方地址。
2. 用户运行环境的 `HF_ENDPOINT` 被设成了官方 `huggingface.co`（非空），上一轮的 `if not os.environ.get("HF_ENDPOINT")` 条件为 False，没覆盖。

最终修复：在 `import sentence_transformers` **之前**设置镜像（官方地址也强制替换为 `https://hf-mirror.com`），import **之后**刷新 `huggingface_hub.constants.HF_ENDPOINT` 常量，并强制 `TRANSFORMERS_OFFLINE/HF_HUB_OFFLINE=0`。三处（embeddings.py、reranker.py、server.py 入口）同步修复，server.py 在任意 huggingface import 前设好作为第一道防线。注意：跑 RAG 是直接 `python server.py` 而非 deploy 脚本（deploy 用本地 models/ + 离线），所以需联网经镜像下载。未提交，待人工确认。

## RAG transformers 版本约束与环境修复

Qwen3-Embedding 的 `qwen3` 架构需要 `transformers>=4.51`，但原 base 环境是 4.49.0 导致报 "model type qwen3 but Transformers does not recognize this architecture"。坑点：
1. 直接 `pip install --upgrade transformers` 会升到 5.x，与项目 `sentence-transformers 4.1.0`（`transformers<5.0`）冲突，并破坏 `smolagents`（`huggingface-hub<1.0`）；且 conda base（`/Users/kirito/miniconda3`）site-packages 无写权限会 `Permission denied`。
2. 正确做法：`sudo python -m pip install "transformers>=4.51,<5.0" -i https://pypi.tuna.tsinghua.edu.cn/simple`，最终装到 `transformers 4.57.6` + `huggingface-hub 0.36.2`（<1.0），与 sbert/smolagents 全部兼容。

结论：RAG 环境要求 `transformers>=4.51,<5.0` 且 `huggingface-hub<1.0`，升级 conda base 需加 `sudo`。pip 警告里的 `~afetensors/~etuptools/~egex` 是之前中断遗留的损坏包目录，可手动 `rm -rf` 清理。每次改完环境/代码都要**重启 RAG 进程**才会生效。

## RAG 异步死锁修复（uvloop + search 阻塞事件循环）

RAG 服务（uvicorn 默认用 uvloop）有两个致命问题，导致 ingest 卡在 CHUNKING、首次检索 HTTP=000 超时：
1. **uvloop 死锁**：async_engine 用 `asyncio.to_thread` 跑阻塞 C 扩展（zvec 的 `create_and_open`、sentence-transformers 模型加载），在 uvloop 下死锁（进程 CPU ~2% 假死，日志停在 `Loading embedding model` 后无进展）。修复：`uvicorn.run(app, host, port, loop="asyncio")` 禁用 uvloop（独立 `asyncio.run` 测试本就正常，印证是 uvloop 问题）。
2. **search 端点阻塞事件循环**：`api/app.py` 的 `search_documents` 在协程里**同步**调 `service.search()`，其内部 `RerankerService.rerank()` 同步加载 710M 的 `BAAI/bge-reranker-v2-m3`，阻塞事件循环使首次检索请求超时。修复：`await asyncio.to_thread(service.search, ...)` 把整个同步 search 丢到工作线程（与 async_engine 一致）。

验证：eee/kb-2/kb-3 三 collection 文档全部 READY（各 24 chunks），`/api/collections/{name}/search` 返回含 `rerank_score` 的结果，端到端打通。换模型/重装后需删 `rag/data/` 重建向量库（documents.db 不自动清理）。未提交，待人工确认。

## 页面检索知识库 500 根因与修复（HTTP/2 vs uvicorn）

现象：前端检索知识库报 500，后端日志 `RAG search failed: 400 - {"error":"Invalid JSON body"}`。
根因：后端 `RagClientConfig.ragHttpClient()` 用 `HttpClient.newBuilder().build()`，**默认走 HTTP/2**；而 RAG 服务（uvicorn/Starlette）只支持 HTTP/1.1。JDK HttpClient 对仅 HTTP/1.1 的服务器发送请求时，请求体被错误分帧，RAG 收到空/乱码 body → `request.json()` 抛 `json.loads` 失败 → 400 "Invalid JSON body"。curl 用 HTTP/1.1 所以一直正常，Java 才复现。
验证：写了最小 Java 程序复刻 `RagApiClient.search`——默认（HTTP/2）返回 400，强制 `.version(HttpClient.Version.HTTP_1_1)` 返回 200。
修复：`RagClientConfig` 的 HttpClient 加 `.version(HttpClient.Version.HTTP_1_1)`。该 bean 被 `RagApiClient` 注入，页面检索和 MCP 知识库检索都走它，一并修复。重启后端后已端到端验证 `/api/v1/knowledge/{id}/search` 返回 200。
经验：**凡后端用 JDK `HttpClient` 调 uvicorn/HTTP1.1-only 服务，必须显式 pin HTTP_1_1**。未提交，待人工确认。
